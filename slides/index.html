Part 1

The Problem

How We Got Here

Monolith

2

Microservices

3

Modular monolith

?

???

Systems started as monoliths. Teams split them into microservices to get autonomy. Many organizations are now moving back toward a modular monolith. Microservices and modular monoliths both split the system by domain, and both have the same problem. Domains overlap, and the overlap has no clear owner. Teams build fit-for-purpose APIs for one screen or one consumer instead of building data products.

Three Real Problems

Discovery

Nobody knows what data exists, or where it lives.

Composition

Combining domains means custom glue code.

Ownership

Overlapping data has no single source of truth.

Discovery: a team can't use data that it can't find. Composition: every new combination of domains needs new code to combine them. Ownership: when two services hold the same data and neither one is the source of truth, the copies drift apart.

Fit-for-Purpose vs. Data Products

Fit-for-Purpose

  • Shaped for one consumer
  • Copies the data it needs
  • Owned by whoever built it

Data Products

  • Shaped around the domain
  • One authoritative source
  • Owned, documented, versioned
A fit-for-purpose API serves today's screen. A data product serves any consumer that needs that domain, including consumers that don't exist yet. The change is from asking “what does this page need?” to asking “what does this domain know, and who owns it?”

The rest of the talk uses one example domain: a conference platform built by four teams. Each team built a service for its own screens. The Speakers team owns speaker profiles. The schedule screen and the feedback screen also show speaker details, so the Sessions and Feedback teams copied the speaker data they needed. The live demo builds this same domain.

Point-to-Point

Five consumers and four services can need up to 20 integrations. Each integration has its own contract, authentication, and error handling. Each consumer has to find out which service has the data, and each consumer writes its own code to combine the results. The AI agent has a dashed border because the talk returns to it in Part 4.

Who Owns “Speaker”?

The Speakers service is supposed to own speaker data. The Sessions and Feedback services copied the fields they needed anyway. The copies now use three different names for the speaker's name. When a speaker changes companies, the Sessions service still shows the old company. An owner on paper is not enough if nothing stops the copies. This is the source-of-truth problem.

Your Newest API Consumer

A Developer

  • Asks a teammate where data lives
  • Reads docs and old code
  • Learns the quirks over time

An AI Agent

  • Only knows what tools describe
  • Has no teammate to ask
  • Guesses when context is missing

An AI agent hits all the same problems.

A developer works around discovery, composition, and ownership problems by asking teammates and reading old code. An AI agent can't do that. It only knows what its tools describe, and it guesses when context is missing. Part 4 returns to this point after the graph is built.

Part 2

One Distributed Graph

Hub and Spoke

In hub and spoke, every consumer connects to one router, and the router connects to each subgraph. Five consumers and four subgraphs need nine connections instead of up to 20. Each consumer learns one graph. Each team owns its own subgraph.

The Vocabulary

Distributed graph
One API composed from many team-owned graphs
Subgraph
One domain's schema and service, owned by one team
Entity
A type that several subgraphs contribute fields to
Router
Plans each query and calls the subgraphs
Composition
Merges subgraph schemas into one, or fails loudly
Supergraph
Apollo's name for the composed distributed graph
“Distributed graph” is the general idea. Apollo Federation is the implementation that this talk uses. “Supergraph” is Apollo's name for the composed result. The GraphQL Foundation is standardizing the same idea in the Composite Schemas specification.

Entities: One Type, Many Owners

This slide uses the same layout as “Who Owns Speaker?”, but with federation. The Speakers subgraph provides the name, company, and bio. The Sessions subgraph adds only the sessions field. The Feedback subgraph adds only averageRating. Each subgraph declares Speaker with @key on the id field, and the router uses the id to join the pieces. No subgraph copies the name or the company, so the data can't drift apart.

Entities: One Type, Many Owners

The panel on the right is what consumers see: one Speaker type with every field. A consumer can't tell which subgraph provides which field.

Life of a Query

  1. Ask: the client sends one query to the router
  2. Plan: the router splits it by subgraph
  3. Fetch: each subgraph resolves its own fields
  4. Join: entity keys link the results together
  5. Respond: the client gets one merged response
The client never knows how many services answered. The router builds a query plan, calls the subgraphs, often in parallel, and merges the results. In the demo, Apollo Sandbox shows the query plan next to each response.

Isn't This Just an ESB?

Classic ESB

  • Business logic lives in the hub
  • One central team owns changes
  • The hub becomes the bottleneck

Distributed Graph

  • The router only plans and routes
  • Teams own schema and data
  • Composition checks enforce contracts

Centralization vs. federation

An enterprise service bus (ESB) was the central integration layer of the service-oriented architecture (SOA) era. Every system connected through it, and it held the routing, the data transformations, and the business rules. One central team usually owned it, so it became a bottleneck. A distributed graph also has a hub, but the router holds no business logic and no data. Each team changes its own subgraph on its own schedule. A schema check in CI, such as rover subgraph check or hive schema:check, stops a change that would break the graph. Every consumer, including AI agents, learns one graph instead of many APIs.

Part 3

Let's Build It

What We're Building

The same four teams, as four subgraphs:

Speakers

Who is talking, plus their bio and company.

Sessions

Talks, times, and who gives them.

Rooms

Where each talk is, and how many it seats.

Feedback

Ratings and comments after each talk.

These are the same four teams from “Who Owns Speaker?”. This time the Speakers subgraph owns the Speaker type. Sessions adds a sessions field to Speaker and links each session to a Room. Feedback adds reviews and averageRating to Session, and averageRating to Speaker. Services refer to each other only by ID, so no service copies another service's data. The four services are written in Java, TypeScript, Go, and Python.

Three Parts of a Distributed Graph

A distributed graph has three parts, and each part has several products to choose from. Solid arrows happen on every request. Dashed arrows happen when a team publishes a schema change. Subgraphs are the services that teams own. Any language works if its GraphQL library supports the Federation specification. The registry stores each subgraph's schema, composes the supergraph, and gives the composed schema to the router. The simplest registry is a file that rover supergraph compose writes. Apollo GraphOS, Hive, and Cosmo add schema checks, history, and usage data. The router takes client queries, plans them across the subgraphs, and merges the results. In the demo, the subgraphs use four languages, the registry is a self-hosted Hive instance in Docker, and the router is the Apollo Router with Hive's plugin.

Part 4

The Graph as AI Context

Why Graphs Suit Agents

  • Typed: the schema says exactly what exists
  • Self-describing: descriptions explain what fields mean
  • Connected: relationships are explicit, not guessed
  • Precise: agents ask for only what they need

The schema is the context.

An agent needs to know what data exists, what the data means, and how it connects. A schema with good descriptions answers all three questions. The demo schemas have a description on every type and field, because the agent reads them to decide what to query.

The Same Hub, for Agents

Tool Sprawl

  • One MCP server per service
  • Tools grow with every service
  • The agent stitches data together

One Graph

  • One MCP endpoint
  • Same tools reach every domain
  • The router does the joins
This is hub and spoke again, applied to agents. Without a graph, an agent needs a set of tools for each service, and it has to combine the results itself. With a graph, the agent connects to one MCP endpoint, and the router does the joins. The demo runs both setups. The REST agent uses four MCP servers, one for each service. Each one is generated from that service's OpenAPI spec with openapi-to-mcp. The GraphQL agent uses one Apollo MCP Server in front of the router.

Apollo MCP Server

  1. Connect: the server reads the schema and calls the router
  2. Discover: search and introspect show types and descriptions
  3. Validate: validate checks a query before it runs
  4. Execute: execute runs the query through the router
The Apollo MCP Server gives AI agents access to a GraphQL API as MCP tools. It can turn predefined operations into named tools, but the demo defines none. Instead, the agent gets four tools. The search tool finds types that match search terms. The introspect tool returns a type with its fields and their descriptions. The validate tool checks a query against the schema. The execute tool runs the query through the Apollo Router. The agent writes its own queries from what it learns. In the demo, the server downloads the current schema from Hive when it starts.

Part 5

In the Real World

Inside Source Allies: Ask Source

New data in the graph makes the agent smarter, with zero AI work.

Ask Source is the internal AI agent at Source Allies. People use it in Slack or in a web UI. It has two tools. The first is a RAG tool over the company's Confluence pages. The second is the Unified Graph, which combines data from HR, time tracking, case studies, Azure, GitHub, and systems that Source Allies built. Most vendor systems only have REST APIs, so the team wrote small GraphQL wrappers over them and added them as subgraphs. When a team adds new data to the graph, the agent can use it right away. Nobody changes the agent, its prompts, or its tools.

Client Story: Agriculture

  • The problem: Many strong APIs, but sprawl makes them hard to find and maintain
  • The approach: One federated graph across their APIs, plus an enablement team to help teams move onto it
  • The result: One experience for consumers, one portal to see and manage every API, and automatic schema conflict checks
This client works in agriculture. They have many well-built APIs, but they have too many to manage. Internal teams struggle to maintain them, and consumers struggle to find out what exists and how to use it. Source Allies is working with them to build one federated graph across their APIs. An enablement team supports each team as it moves onto the graph. The outcome is one consistent experience for consumers and one portal to see and manage the APIs. Composition checks also catch schema conflicts automatically.

Client Story: Education

  • The problem: Rewriting many systems, backend included, with AI assistants for students as a priority
  • The approach: Distributed GraphQL instead of distributed REST services
  • The result: The graph built for the web and mobile rewrites serves AI with almost no extra work. The AI agent is months ahead of schedule.
This client runs an education platform. They were rewriting many of their systems, including the backend. One priority was making their data easy for AI to find and use, so they could build AI assistants for students. Source Allies worked with them to adopt a distributed GraphQL backend instead of distributed REST services. The graph that the web and mobile rewrites needed anyway now supports their AI work with almost no extra effort. Their AI agent work is months ahead of schedule. The agent quickly finds the data that students and admins need.
